# J3 distributed pre-prod deployment and measurement plan

Status: **planning only**. No distributed pre-prod environment exists as of 2026-11-20. This plan prepares the first demo pre-prod capacity gate; it does not authorize a production rollout or turn the HLD's 5,000/10,000/15,000 accepted-events/s goals into measured results.

The [J3 benchmark contract](j3-plan.md) supplies workload durations, thresholds, and repeat counts. The [local full-population recheck](j3-population-after-batch-2026-11-20.md) proves setup and configuration projection on one host, not distributed admission or delivery capacity. `deploy/` currently supplies a single-host Compose functional stack, with no distributed deployment definitions. Its [topic script](../../deploy/kafka/create-topics.sh) creates one partition and replication factor one; those values are local defaults, not proposed pre-prod counts.

## Decisions and inventory needed before provisioning

Choose a disposable, isolated pre-prod account/project, platform (VMs or an orchestrator), region and failure domains, infrastructure owner, cost ceiling, data-retention/teardown date, and network access method. Record these in the run record without credentials or connection URLs. Keep the latter in ignored env files or the chosen external secret manager. The first architecture decision is whether the current one-logical-shard routing/deployment path can support the proposed multi-shard layout; if not, implement and test that path before claiming a distributed shard benchmark. Bucket moves remain disabled.

| Component | Inventory to record before a profile | Required separation or check |
|---|---|---|
| Load generators | Host count, CPU/RAM/network, Node version, clock source, planned rate per host, achieved no-skip ceiling | Separate from RelayForge and receivers; capacity to schedule the 15,000/s target with headroom |
| Webhook receivers | Host count, CPU/RAM/network, latency/failure configuration and measured distribution | Separate from workers; measured ability to absorb up to the planned 49,500 attempts/s without becoming the hidden bottleneck |
| API and asynchronous roles | Image digests, replica counts, CPU/memory limits, pool sizes, worker and publisher limits, placement | Independent ingestion, control, router, delivery, retry and analytics processes; no unrecorded shared host saturation |
| PostgreSQL 17 | Control, ingestion and delivery database/shard placement; primary/standby topology, storage, WAL archive, connection limits, write endpoint | Verify ingestion synchronous standby acknowledgement before `202`; record standby state and commit latency. A standby does not add primary write capacity. [PostgreSQL synchronous replication](https://www.postgresql.org/docs/17/warm-standby.html) |
| Kafka | Broker placement, topic keys, provisional partition and replication counts, `min.insync.replicas`, retention, consumer groups | Use a multi-broker test topology; measure partition skew and lag before choosing final counts. [Kafka topic configuration](https://kafka.apache.org/41/configuration/topic-configs/), [consumer lag](https://kafka.apache.org/41/operations/basic-kafka-operations/) |
| Redis and ClickHouse | Node placement, resources, versions, persistence/retention, query limits | Record cache hit/miss and analytics ingest/query latency; a single ClickHouse node remains an explicit limitation until a distributed topology is implemented |
| Observability | Metrics/log collection, clock sync, dashboard/query access, sampling interval and retention | Include per-host CPU, memory, network, disk, throttling, and all service/database/broker counters |

If Kubernetes is chosen, record container requests and limits as well as observed throttling and placement; its scheduler uses requests for placement. [Kubernetes resource management](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/) No provider, machine size, shard count, partition count, or replica count is selected by this document. They are provisioning inputs to vary and measure, then review.

## Work sequence and gates

| Step | Deliverable | Gate to advance |
|---|---|---|
| 1. Provision | Versioned, reproducible infrastructure definition and teardown; private service networking, controlled generator/receiver access, persistent volumes, external secrets, immutable image digests | Inventory above filled; deploy and teardown rehearsed; no local Compose project presented as the distributed environment |
| 2. Deploy data plane | PostgreSQL 17 databases with ingestion synchronous standby, Kafka broker/topic topology, Redis, ClickHouse, then service images with explicit shard locators and resource/pool limits | Health/readiness checks pass; topic partitions/replicas and shard map recorded; no silent fallback from synchronous acceptance |
| 3. Prove correctness | Run Java 21 `mvn verify` and existing functional/HA acceptance before deploying a tested image; run J1 flow and relevant J2 outage/duplicate/lease checks in pre-prod; populate 100 organizations and 10,000 endpoints | All 10,000 subscriptions project, 300 match the test event type, 9,700 remain idle, control outbox is clear, and relevant consumer lag is zero before each measured run |
| 4. Prove instruments | Dry-run coordinated producers and receivers; collect service, PostgreSQL, Kafka, Redis, ClickHouse and host snapshots before/after; verify UTC clock skew and aggregation | No generator skips or missing/invalid service samples at a bounded calibration rate; receiver latency/failure mix and actual attempt ratio reported |
| 5. Run J3 profiles | Independent normal, peak and headroom repeats below, each on an equivalent starting state; preserve commands, manifests without secrets, raw outcomes, snapshots and image/config versions | Every repeat evaluated separately against the full [J3 contract](j3-plan.md); a missing measurement or failed repeat is **unmet** |
| 6. Analyze and decide | Per-stage bottleneck analysis, variance across repeats, provisional topology changes with new repeats, sanitized reproducible report | Only passing measured evidence may set production shard, partition, replica and concurrency choices; otherwise keep J3 and first-release gate open |

Deployment automation, multi-broker topic creation and distributed service-side collection are **work to implement**, not existing capabilities. The current `load-tests/benchmark.py` samples one local Compose project. Before Step 4, add a collector or adapters for the chosen platform that records the same service-side facts with bounded timeouts and nonzero exit on missing data. Preserve the existing coordinated producer format in `load-tests/aggregate_producers.py`; it validates producer outcomes but does not prove delivery completion. For PostgreSQL, include `pg_stat_activity`, `pg_stat_replication`, `pg_stat_wal`, locks, storage and pool utilization; counters require before/after differences and can reset after restart. [PostgreSQL statistics](https://www.postgresql.org/docs/17/monitoring-stats.html) For ClickHouse, collect ingest/query and table-part evidence from its system tables. [ClickHouse system tables](https://clickhouse.com/blog/clickhouse-debugging-issues-with-system-tables)

## Profile execution and evidence

Use the existing planned workload: 100 organizations, 10,000 active endpoints, three matching subscriptions per event on average, 1 KiB serialized requests, a documented hot-tenant slice, receiver latency centered near 200 ms, and retryable failures chosen to **measure** an attempt ratio near 1.1. Do not assume the configured receiver failure percentage produces exactly that ratio. Capture achieved fan-out, latency distribution, retries and attempts. Verify the receiver can sustain the attempted-request rate independently of RelayForge before using delivery lag as a service result.

| Profile | Scheduled arrivals/s | Duration per repeat | Repeats | Planned attempts/s at 3 × 1.1 |
|---|---:|---:|---:|---:|
| Normal | 5,000 | 1,800 s | 3 | 16,500 |
| Peak | 10,000 | 300 s | 3 | 33,000 |
| Headroom | 15,000 | 120 s | 3 | 49,500 |

Warm for two minutes before each repeat, start producers on the same future UTC instant, stop scheduling at the specified duration, and retain at least five minutes of bounded post-run observations. The backlog must drain within 120 seconds to pass even though observation continues. Reset to an equivalent state before the next repeat; never average a failed repeat into a pass. Use explicit process deadlines and at most two attempts at a failing operation, then record the exact failure. The nine measured windows alone total 111 minutes; warm-up and five-minute observation add 63 minutes, so reserve **at least 174 minutes** plus provisioning, resets and analysis. At 100% target admission, the nine windows schedule 41.4 million events, implying 124.2 million logical deliveries and about 136.62 million attempts before warm-up and retries beyond the planned ratio. Provision storage and cleanup capacity for that scale; these are arithmetic inputs, not achieved counts.

For **each repeat**, report scheduled, sent, skipped, durable `202`, non-202 and transport-error counts; accepted-event p50/p95/p99; actual fan-out and attempts per delivery; delivery completion lag p95/p99; delivery throughput and drain time; dead letters/retries; outbox age; Kafka lag by topic/group/partition; PostgreSQL CPU, connections, locks, WAL and disk growth; Redis hit/miss/memory; ClickHouse fact counts and dashboard-query latency; host resource pressure; and I4 cleanup progress. Join delivery state to the authoritative event acceptance timestamp. Preserve sanitized raw records and sampled evidence so each reported percentile and count can be regenerated. The J3 pass thresholds remain those in [the benchmark contract](j3-plan.md), including at least 99% scheduled arrivals returning `202` in-window, no generator skips, accepted-event p95 ≤ 500 ms/p99 ≤ 1,000 ms, delivery lag p95 ≤ 5 s/p99 ≤ 30 s, and complete backlog drain within 120 s.

## First action when an environment is funded

Select the platform and owner, fill the inventory table with provisional resources, and provision Step 1 as an isolated, disposable environment. Review cost and storage estimates against the 41.4-million-event schedule before applying infrastructure changes. Then implement the platform deployment and collector in separate reviewable tasks; run a bounded calibration before the full profiles. Until that evidence exists, J3 and the first demo pre-prod release gate remain open.
