# C1 event acceptance and durability

`POST /v1/events` derives the organization and effective `events_per_minute` limit from the control plane's scoped `/v1/auth/check` response. It never accepts an organization ID from the request or reads control-plane tables. If the control plane is unavailable, authentication fails closed. The control-plane URL is read from the ignored `.env` through `CONTROL_INTERNAL_URL`.

The endpoint reads at most the configured body limit before JSON parsing. Strict parsing rejects duplicate fields, trailing JSON, excessive nesting, and oversized strings. The request hash is SHA-256 of RFC 8785 canonical JSON over `event_type`, resolved `schema_version`, `data`, and normalized supplied `occurred_at`. Numeric values outside the exact I-JSON integer range and invalid Unicode are rejected. The hash format is versioned in the idempotency registry.

The active bucket fence, idempotency registry, event, rate counter, and ingestion outbox commit in one ingestion-owned transaction. A matching unexpired key returns its original event ID; a changed body conflicts; after 90 days the key can be reused. The registry lock uses the database clock after contention. The event locator carries version, bucket, map epoch, both logical shard IDs, acceptance day, and event UUID. Initial epoch-one fences represent the local single-shard bootstrap; future bucket moves require the separate stale-map and cutover gate in the checklist.

Production acceptance requires PostgreSQL `fsync=on`, `synchronous_commit=on`, a named synchronous standby, and a currently synchronous replication connection. The application checks before and inside the transaction and uses bounded database and request timeouts. A commit timeout has an unknown outcome; clients must retry with the same idempotency key. The normal single-Postgres Compose stack has acceptance disabled and returns `503` for authenticated publishes. The `deploy/ingestion-ha/` overlay enables acceptance with a named standby and verifies a successful `202`, idempotency, and failure when the standby stops. This follows [PostgreSQL 17 synchronous replication guidance](https://www.postgresql.org/docs/17/warm-standby.html) and [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785).
