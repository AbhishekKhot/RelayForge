# D1 outbox publication

Each owner publishes only its own PostgreSQL outbox: control, ingestion, or delivery. A shared repository selects at most one due row per polling cycle with `FOR UPDATE SKIP LOCKED`, updates it to `IN_FLIGHT`, assigns a random claim token and 30-second lease, and increments the attempt count in one short database statement. An expired lease is eligible for a new claim. This is a queue use of PostgreSQL's [locking clause](https://www.postgresql.org/docs/17/sql-select.html); `UPDATE ... RETURNING` supplies the claimed row after the change ([PostgreSQL 17](https://www.postgresql.org/docs/17/sql-update.html)).

The publisher sends outside a database transaction. It marks a row `PUBLISHED` only after Kafka acknowledges the record and only while its claim token still matches. A failed send returns the row to `PENDING` with bounded jittered backoff and a short diagnostic code. If Kafka acknowledges and the process fails before the database update, lease recovery sends the same envelope again. Consumers must deduplicate its stable `message_id`; D2 implements their quarantine and deduplication paths.

The envelope uses the outbox UUID for `message_id` and, until source request IDs are stored, for a stable transport `correlation_id`. It includes schema version, organization and aggregate IDs, creation time, and a JSON-object payload capped at 64 KiB. A row missing tenant identity or carrying malformed/oversized JSON is never sent; it remains observable with a bounded retry code for the D2 quarantine workflow. Messages and diagnostics contain no endpoint secrets or response bodies.

Kafka producers require `acks=all` and idempotence, cap metadata and acknowledgement waits, and use each row's stable topic and partition key. The first implementation uses a single-row batch so the 10-second acknowledgement wait fits inside its 30-second lease. Parallel batch sizing is a measured capacity task. These settings follow the [Kafka 4.1 producer configuration](https://kafka.apache.org/41/configuration/producer-configs/). The event-accepted topic uses the opaque event locator key as specified by LLD §7.3 and the ingestion outbox.
