# B2 endpoint authentication configuration

Endpoint registration accepts `NONE`, `STATIC_HEADER`, `STATIC_API_KEY`, `BEARER`, `BASIC`, `TOKEN_EXCHANGE`, and `CLIENT_CREDENTIALS`. A static header uses `header_name` and `value`; Bearer uses `token`; Basic uses `username` and `password`. Token exchange uses the LLD's `token_request`, `token_response`, `token_placement`, and `secrets` structure. Client credentials uses `token_url`, `client_id`, `client_secret`, optional `scopes`, and `token_response`. Dynamic token URLs follow the same SSRF policy as webhook destinations. Token extraction paths are definite property/index paths only. The worker will execute these configurations in G1; registration validates and stores them without calling a customer token service.

Secret-bearing authentication JSON is encrypted before inserting an endpoint. Each encryption uses a fresh random 256-bit data key, 96-bit AES-GCM nonce, and 128-bit tag. Associated data binds organization ID, endpoint ID, field name, and configuration version. A versioned key-encryption service wraps each data key; the local provider also uses AES-GCM with a fresh nonce. The database stores ciphertext, wrapped data key, key version, and nonce. `NONE` stores no auth ciphertext. The minimal endpoint read returns only the auth type. The same cipher supports signing-secret encryption for B3's issuance and rotation endpoint.

The local/test provider reads `RELAYFORGE_ENCRYPTION_LOCAL_KEYS` as comma-separated `version:64-hex-character-key` entries and `RELAYFORGE_ENCRYPTION_ACTIVE_VERSION` as the active version. The Compose values come from ignored `.env` settings `ENDPOINT_LOCAL_KEK_KEYS` and `ENDPOINT_ACTIVE_KEK_VERSION`. Startup fails if the active key is missing or malformed, or if the local provider is used outside `local`/`test`. Production requires a `KeyEncryptionService` backed by a managed key service; no production key is embedded in the application.

Flyway V3 adds `encryption_key_checks`. After migration and before readiness, startup verifies a wrapped canary for every retained key version and creates one for a newly selected active version. Reusing a version with different key material fails startup even when the new key has valid syntax. The canary is a wrapped public test value, not a stored secret.

For local wrapping-key rotation, generate a fresh 32-byte key in the ignored `.env`, add it under a new version while retaining old keys, and select the new active version. New endpoint configurations use the new version. The `EndpointSecretCipher.rewrap` operation can rewrap existing data keys without changing their ciphertext. Keep an old key and its canary until all rows and retained backups that depend on it are rewrapped or expired; then retire both. Key loss makes the affected configuration unreadable; do not replace a missing old key with a new value under the same version.

This design follows the [Java 21 AES-GCM API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/javax/crypto/Cipher.html) and [OWASP cryptographic storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html).
