# Endpoint management contract

Endpoint and subscription lists use a tenant-scoped, UUID-ordered cursor with a maximum page size of 100. A page reads one extra row to decide whether to return `next_cursor`. The ordering is explicit so PostgreSQL `LIMIT` does not return an unpredictable subset. [PostgreSQL 17 LIMIT documentation](https://www.postgresql.org/docs/17/queries-limit.html).

Endpoint updates and signing-secret rotation require a strong `If-Match` entity tag containing the current numeric version. A missing precondition is rejected; a stale version returns `412`. The database update includes organization ID, endpoint ID, and expected version in its predicate, then returns the new version. This makes concurrent updates safe and keeps cross-tenant guessed IDs indistinguishable from absent IDs. [RFC 9110 conditional requests](https://www.rfc-editor.org/rfc/rfc9110.html), [PostgreSQL 17 UPDATE](https://www.postgresql.org/docs/17/sql-update.html).

Registration, update, and rotation commit the endpoint row, redacted audit record, organization configuration revision, and secret-free `control_outbox` snapshot in one transaction. The snapshot contains endpoint status/version and subscription IDs, event types, statuses, and versions. The delivery projection and worker consumption are D3 work; until then, the outbox records the durable change but cannot prove a worker observed it. [Spring programmatic transaction management](https://docs.spring.io/spring-framework/reference/data-access/transaction/programmatic.html).

Authentication and signing ciphertext retain their own encryption configuration version. V4 backfills existing authentication rows to version 1. An unrelated endpoint update increments the endpoint version without changing either ciphertext AAD version. Rotation or explicit authentication replacement records a new configuration version. Secret values appear only in the rotation response and never in endpoint reads, audit records, or configuration snapshots.
