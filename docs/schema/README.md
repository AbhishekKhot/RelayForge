# PostgreSQL physical schema plan

The SQL files in this directory are the reviewed physical V1 schema templates for PostgreSQL **17**. Their executable V1 Flyway copies live in `relayforge-control-plane`, `relayforge-ingestion`, and `relayforge-delivery-api` under `src/main/resources/db/migration/`. Control-plane V2 adds `provisioning_requests` for the A3 safe recovery path; see its migration and [decision record](../decisions/organization-provisioning.md). Each owner applies its migrations to its own database; ingestion and delivery run them on every shard. Each database has its own Flyway history, credentials, backups, and write endpoint. Local Compose can host the three databases on one PostgreSQL instance; production shard count remains a measured capacity choice. PostgreSQL 17 has an active support window and supports the partitioned constraints used here ([version policy](https://www.postgresql.org/support/versioning/), [partition rules](https://www.postgresql.org/docs/17/ddl-partitioning.html)).

## Keys and ownership

- `control-plane.sql` owns accounts, credentials, endpoint and subscription configuration, bucket mapping, account audit, and its outbox. These records are not subject to event-age deletion.
- `ingestion.sql` owns the bucket fence, 90-day idempotency registry, accepted event payloads, and ingestion outbox. The registry has a global key within its shard, `(organization_id, idempotency_key)`; it is not partitioned by event day. The event table uses `(accepted_day, id)` as its partition-compatible primary key.
- `delivery.sql` owns endpoint/subscription projections, routing snapshot/progress, delivery state, active `delivery_work`, attempts, replay records, event-specific audit, and delivery outbox. Historical parents partition on immutable UTC `accepted_day`; keys and local foreign keys carry the day. The unpartitioned work table indexes due/leased deliveries and stores their exact `event_expires_at` so claims do not scan every history partition or start after expiry; it is inserted, updated, or removed in the same local transaction as its delivery row. Cross-service IDs have no database foreign keys and are verified at message/API boundaries.
- Published outbox rows are deleted only after broker acknowledgement and the recovery window; pending or in-flight rows are retained and alarmed. Outboxes are deliberately outside event-day partitions so old unpublished work cannot disappear through a partition drop.

The physical SQL supersedes the LLD's earlier single-database field examples. It keeps the same logical fields where compatible, while replacing UUID-only partitioned keys and cross-service foreign keys. The payload remains in ingestion PostgreSQL with a 256 KiB API cap. Router and worker use the versioned locator and authenticated internal read contract; they never store a second authoritative payload. [PostgreSQL unique keys on partitions](https://www.postgresql.org/docs/17/ddl-partitioning.html) must contain the partition column.

## Partition creation and retention

Schema bootstrap creates yesterday, today, and seven future UTC-day partitions. A maintenance job must create the next seven days on every shard before midnight UTC; there is no default partition. A missing future partition blocks acceptance or routing with a retryable service error and an operational alert. The job verifies attached partitions and indexes after creation. Run this maintenance outside request transactions.

The logical history cutoff is **2,160 hours** after `accepted_at`, independent of client `occurred_at`. API queries hide expired history, replay rejects it, and workers stop starting outbound attempts for expired events. Physical deletion uses a documented **up to 25-hour normal grace**: after a complete UTC day has passed its 90-day cutoff, detach and drop that day's partitions in dependency order. This avoids deleting hundreds of millions of rows from the partially expired day. The scheduled job starts at 00:15 UTC and only selects a day whose upper bound is at or before the exact cutoff. If a day is blocked, the grace target is missed and an incident is raised; no work is silently deleted.

Before detach, assert that the day has no `delivery_work` rows, no incomplete `routing_progress`, no live replay/lease, and no `PENDING` or `IN_FLIGHT` ingestion/delivery outbox record. Expired active work is explicitly terminalized and its final facts published before these checks. Drop delivery child partitions in this order: `delivery_audit_records`, `replay_requests`, `authentication_attempts`, `delivery_attempts`, `deliveries`, `routing_targets`, `routing_progress`; then the matching ingestion `events` partition. The cross-database order is operational, not a transaction. Recheck blockers before each detach. Use `DETACH PARTITION ... CONCURRENTLY` outside a transaction when supported by the actual schema, complete an interrupted detach with `FINALIZE`, and drop only the detached table. The schema has no default partitions because concurrent detach forbids them ([PostgreSQL ALTER TABLE](https://www.postgresql.org/docs/17/sql-altertable.html)).

Expire registry rows in small indexed batches by `expires_at`; do not use event partition drops to enforce key expiry. Capture database `clock_timestamp()` after lock waits for acceptance/expiry decisions. At the sustained planning rate, the 90-day registry alone can approach **38.88 billion live rows globally**. The final load suite must measure registry insert, conflict lookup, expiry-delete rate, WAL, vacuum, and disk before any production topology or throughput claim. A failed cleanup benchmark requires a revised storage plan, not an untested shard count.

## Migration and verification order

1. Pin the same PostgreSQL 17 minor image for Compose and migration tests; the current test image is `postgres:17.11`. Upgrade it deliberately. Provision one database and restricted application role per owner. Seed the 4,096-bucket map and shard-local fences only after logical shard IDs are assigned.
2. Apply each owner's schema through its own forward-only Flyway history. Create/verify upcoming partitions on each shard, then enable owner readiness. Bootstrap endpoint and subscription projections from control plane, then catch up the organization-revision change stream before routing becomes ready.
3. Test duplicate keys across UTC-day boundaries and expiry, wrong-organization local FK rejection, absent partition failure, replay against an old cohort, blocked retention, and clean restart. Test that all event reads and writes use the locator's shard and day.
4. Run the full Docker functional suite before normal, peak, and headroom load tests. Report row size, per-shard writes, WAL, storage, vacuum, retention duration, and tenant skew; size physical shards only from those measurements.

The SQL templates match their V1 migrations. Bootstrap pre-creates yesterday, today, and seven future daily partitions. Ongoing partition pre-creation, retention detach, failover, and backups remain operational jobs to implement and test. ClickHouse retention is unchanged by this PostgreSQL plan.
